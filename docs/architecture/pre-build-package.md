## A. Final architecture summary

EGO is an installable, repository-level, model-agnostic Agentic Engineering Control Plane kernel: the kernel a platform could later wrap, not the PRD platform. Objectives, in priority order: one behavioural contract across products, repositories and models; high assurance at low context cost; human-readable control with deterministic enforcement; task state over model session; explicit human authority.

**Seven concepts that are never conflated.**

```
GLOBAL INSTALLATION                 is a bootstrap / launcher convenience
PROJECT PIN + VERIFIED CONTENT HASH is the execution identity
REGISTRY                            is transport
CACHE                               is immutable
MODEL                               is intelligence
RUNTIME ADAPTER                     is integration
EGO KERNEL                          is governance
```

**Two hashes, two roles.** `runtime_sha256` is the canonical release integrity hash: sha256 over the internal manifest, which lists every runtime file with its hash in sorted order, excluding only the `name` field of `package.json` and all release-time metadata; `package.json` is otherwise a runtime file and its `version` is hashed, so distinct version strings always yield distinct runtime identities. It is computable identically from an extracted install and from a tarball, it is `ego.integrity` in the pin, the cache directory name, the launcher equality test, and what `ego version` prints. `tarball_sha256` is the hash of `ego-X.Y.Z.tgz` listed in `SHA256SUMS`; it verifies transport only. The external `manifest.json` records both. A re-scoped package is a different tarball with its own transport metadata; when its runtime files are identical its runtime identity is identical, which is what "scope never affects behaviour" means. A released version string such as `1.2.0` identifies exactly one official runtime identity; local and development builds carry an explicit development identity `1.2.0-dev.<git-sha>` (a SemVer prerelease, deterministic from the commit), so no unofficial build can present itself as an official version. The index may hold several acquisition records for one runtime identity, never several runtime identities for one version string, official or development. Development builds are the release build with `SOURCE_DATE_EPOCH` set from the commit timestamp, refused on a dirty tree, so a development identity is reproducible from its commit.

**Source repository versus distributed product.** EGO is developed in its own repository with its own CI/CD and released as one signed artifact set. Users never clone EGO into products. Online: `npm install -g @tarscoff/ego` then `ego init`. Offline: `npm install -g ./ego-X.Y.Z.tgz` then the same commands under declared offline mode. Runtime floor Node ≥ 24, hard-checked by the launcher.

**Shape of the source repository.**

```
EGO/
├── AGENTS.md  CLAUDE.md(@AGENTS.md)  README.md  CHANGELOG.md  HARNESS_CATALOG.md (generated)
├── control-plane/      authored Markdown: modes, intents, permissions (absolute-denies, capabilities, grants),
│                       secrets taxonomy, lexicon, skills defaults and sources, validations, reviewers, surfaces,
│                       risk, documentation surfaces, workspace/coordination constants, profiles, decision-gate
│                       config, release-keys.md (absolute-core file, seed of the machine trust store)
├── policies/           baselines/<domain>, frameworks/<framework>, templates, schemas, tension links,
│                       generated/ (compiled AST, obligations, compiled authority table), tests
├── skills/             core/ (family skills), organizational/, external/ (lock), product-template/
├── packages/           kernel, cli (launcher + launcher set), adapter-claude-code, adapter-codex-cli, forge,
│                       benchmark, docx-adapter (optional, isolated)     → built into ONE distribution
├── templates/          repository-overlay, workspace, stakeholder-packs, skill, task
├── runtime/posix/      hook shims only (fail closed when `ego` is not resolvable)
├── tests/              unit, integration, conformance, adversarial (incl. network-free suite), benchmark, fixtures
└── docs/               getting-started, user-guide, installation, releases, admin, maintainer-guide, architecture,
                        adr, concepts, policies, skills, integrations, multi-repo, security, benchmarking,
                        troubleshooting, stakeholder-contributions, extending-the-harness
```

**Three kinds of truth.** Authored: control plane, policies, overlays, organizational skills, workspace registry, decision records. Generated: compiled policy AST, obligations and the compiled authority table, adapter configs, catalog, registries, scoped instruction files, compatibility and capability manifests, and the pin file `.harness/harness.md` (written only by `init`, `upgrade`, `rollback` and `sources add|remove`; hand edits detected by its provenance stamp). Runtime: `.harness/runtime/` per developer machine; gitignored, never canonical.

**One kernel, many surfaces.** Natural chat, slash shortcuts, the `ego` CLI (alias `ego`), the `claude-code` adapter, the `codex-cli` adapter, git hooks and CI all call the same TypeScript kernel: one bundled dependency-free JavaScript file. Adapters translate runtime events and expose runtime UX; they contain no policy, permission, task, claim, decision, completion, grilling, benchmark, secret or distribution logic. The capability matrix is keyed by host identifier (`claude-code`, `codex-cli`), never by model.

**Invariants.** INTENT ≠ AUTHORITY. MODEL RECOMMENDATION ≠ HUMAN AUTHORIZATION. Task durable, session disposable, ownership explicit, human authority explicit. IDE-open folders never define the workspace. Forge issues are the canonical task source for issue-driven projects. Local runtime state is never pushed and never canonical. Absolute denies cannot be widened by any lower layer. Generated artifacts are never edited by hand. A malformed control-plane file fails closed. Risk may escalate after work starts and is never grandfathered. Same EGO runtime identity + same compiled policy + same profile + same task and workspace = same governance contract, regardless of model. LOCAL-FIRST: no mandatory service; EGO emits no telemetry and no remote error reports; EGO-authored code (launcher and runtime) makes no network activity, direct or by spawning a network-capable tool, outside the four classified capabilities forge, sync, skills and model-through-runtime.

## D. Final task / forge issue model

- Task source per workspace or repo: `issue-required` | `issue-preferred` | `ad-hoc`; `init` proposes `issue-preferred` when a supported tracker with open issues is detected; under declared offline or an unreachable forge, `init` infers the tracker from the remote URL only and says "open issues not checked".
- The forge issue owns identity, title, description, criteria, labels, dependencies, discussion and status. GitHub and GitLab first; Azure DevOps work items as an extension; Bitbucket has no issue API.
- The local task is continuity only: `<provider>:<repoId>:<n>` with provider, repo identity, issue number, URL and fetched revision, in `.harness/runtime/tasks/`, per developer.
- Lifecycle: forge issue → local task → implementation and local commits under the overlay's branch strategy → fingerprinted validations → Grilling at tier ≥ 2 (deterministic preflight always; model-assisted review per Q89) → completion gate → receipt. DONE, PARTIAL, BLOCKED, FAILED. Local DONE never closes the issue.
- Criteria: extracted from configurable headings and task lists; if absent, proposed from issue and repository context, approved in chat, persisted when authority exists; proposal UNAVAILABLE without a model per Q54.
- Freshness at task start, session start with an active task, resume, adopt, before DONE, and at most every ten minutes; under declared offline every check is recorded NOT_CHECKED(offline); "reconnect" means the mode is unset or `issue refresh` is run explicitly. Offline, `issue show` serves the cached revision with its age; `issue list|next|take|bind` report UNAVAILABLE(offline) with the exact command to run once connected.
- Selection: open, unassigned or mine, role-label mapping, not blocked (native links, `blocked` label, `Depends on #N`), then priority, milestone, age. "What is the next" shows; "Take the next" authorizes. Assignment asked, never silent.
- Multi-repo resolution through the registry's default tracker, per-repo overrides, `backend#142`, URLs; ambiguity asks.
- Forge unreachable or declared offline: STANDARD continues on the cached snapshot with disclosure; STRICT+ may continue on the snapshot but DONE is blocked until a fresh check succeeds.
- Exempt by default: consolidation, benchmark, maintenance, governance maintenance, administrative workflows.
- All issue, comment and PR text is untrusted.

## E. Final local session / multi-session model ("held scopes")

- One runtime root per logical workspace in the main worktree of the workspace root, resolved through the registry and `git rev-parse --path-format=absolute --git-common-dir`; every registered repo and worktree, and both hosts on the same filesystem, share sessions, tasks, claims, conflicts, ledger, evidence and pending decisions.
- **Runtime consistency.** The first runtime to open a root writes `.harness/runtime/stamp.json` with its runtime identity and runtime-state schema version (the schema of every record class: sessions, tasks, claims, conflicts, ledger, presentations, tokens, leases). On every run outside the launcher set the launcher compares the checkout's pin and the executing runtime's compatibility matrix with the stamp: a runtime that cannot read the stamp stops with the same BLOCK and migration guidance as `rollback`; the stamp is rewritten only by `upgrade` or by `sync` (when every AVAILABLE member's pin can read the newer schema). Pins are per repository (thin, standalone-capable). **Divergence.** A workspace is divergent when any two AVAILABLE members' `ego.integrity` differ; KNOWN_BUT_UNAVAILABLE members are listed in the warning, never compared. Compatible divergence means every AVAILABLE member's pinned runtime can read the stamp's runtime-state schema; any other divergence is the launcher BLOCK, for read-only work too. Read-only analysis and discovery tolerate compatible divergence with a visible warning in every profile. Mutation rule, every profile, evaluated as the first step of the held-scopes predicate before the own fast path: the predicate BLOCKS any write or `claim add` whose path resolves to a repository whose `ego.integrity` differs from the executing runtime identity (always the pin of the repository the session was launched in) or from the pin of any repository the task has already mutated or claimed, with a message naming both identities and `ego upgrade --workspace`; `task adopt`, `task resume` and `handoff` are refused when the adopting session's executing runtime identity differs from the pin of any repository the task has claimed or mutated. STRICT additionally refuses `task open` and `issue take` when the task's affected repositories diverge, where affected repositories at open are the launch repository plus the repositories of scopes passed to `task open` or `claim add` and any repositories the bound issue names. HIGH_ASSURANCE refuses any governed mutation in a divergent workspace. `sync`, `doctor`, `upgrade --workspace` and `rollback --workspace` are exempt from the divergence block in every profile: they are its remedy and touch only `.harness/` and generated artifacts. A multi-repository task therefore never crosses repositories under different governance implementations.
- Records with one writer class each: session records owner-written; claim records lock-written; task coordination lock-written; closed markers create-only; ledger and conflict logs append-only. Commits, dirty paths and surfaces derived on read.
- Ownership: a task owns scopes; exactly one live session holds them; repository and path scope are enforced; surface is an alias; work package is a label.
- Pure predicate: superseded, subagent bound, own fast path, foreign overlap with peers skipped, structured deny with exact commands, lock-protected auto-claim. Foreign claims are never overridden implicitly.
- Liveness on the session (heartbeat; `claude-code` adds pid and start time; `codex-cli` TTL-only). Alive-but-silent blocks until `--force`, refused while the holder has an open tool window on the scope.
- Enforcement: path-known writes denied before execution; Bash writes detected at PostToolUse, recorded on both tasks, surfaced, blocking Stop; three pre-denied Bash classes; STRICT read-only allowlist rule when another live session shares the checkout or frozen paths exist; HIGH_ASSURANCE prefers worktree isolation and refuses a second live session in a bound checkout.
- Subagents: no records, claims or authority; bound to the parent's explicit scopes; agent identifiers kept as ephemeral trace identity. `codex-cli` freeze rule until conformance.
- One primitive for crash, handoff and resume: `harness task adopt`; `harness handoff --to codex-cli`; compaction needs nothing.
- Remote participants: separate environment; shared truth is git, forge issues, committed configuration, explicit handoff; checks rerun on return; receipt states execution outside the local boundary. No synchronization service.
- Completion additions: no scope held, no unresolved conflict, peers reconciled, no handoff in flight, no other live session bound, no open window.
- Invisible until a real conflict or a human decision.

## G. Final human decision gate model

## H. Final authority / security model

- Precedence: ABSOLUTE CORE DENY > ORGANIZATION POLICY > HARNESS PROFILE > PRODUCT OVERLAY > TASK GRANT (ASK→ALLOW only, current task) > MODEL DECISION. Lower layers narrow, never widen. `absolute-denies.md` and `release-keys.md` are absolute-core files no lower layer may reference or modify; they change only in the EGO source repository.
- Compiled authority table (generated, reproducible): per profile × authority mode × permission ID verdict, absolute-deny set, grant verb table, protected-path set, pre-denied command classes, STRICT read-only allowlist, sanitizer locked minimums, operation→ID matchers. It is the object `ego capabilities` renders, `explain capability` justifies, and CI diffs for `authority_changes`. On upgrade, a new child permission ID inherits the consumer overlay's verdict for its parent unless set explicitly.
- Capability families with narrow three-valued IDs: local filesystem with protected paths; local commands by class; git local; git remote with push, force-push, tag push and remote deletion denied; forge read; forge narrow write (review comment, thread reply, thread resolve); forge deny (PR create, modify, close, merge, self-approve, release, protected branches, branch rules, repo permissions); issues (read ALLOW, comment and assign ASK, create, edit, transition, close DENY); local database, containers, Kubernetes per task; production fully denied; MCP local per class and remote discover, read, narrow-write, mutate separately, unknown endpoints denied; network classes with allow and deny lists; EGO's own network uses classified as `forge`, `sync`, `skills`, `model-through-runtime`.
- Enforcement layers: repo-side git hooks; agent PreToolUse deny in both hosts; compiled policy cache; `harness verify --range` in CI or pre-receive; managed tier for HIGH_ASSURANCE.
- Secrets: Markdown taxonomy; structured curl parsing; redaction before logging, delegation, evidence, MCP, docs, diagnostic bundles and local error reports; locked core minimums; registry and source tokens never written to project files, logs or receipts; EGO emits no telemetry.
- Human-gate integrity: prevent in-band, detect out-of-band, managed tier in HIGH_ASSURANCE.
- Release integrity: Ed25519 per-key signatures over `SHA256SUMS`; machine-local trust store seeded under bootstrap trust and extended only by cross-signed releases; explicit revocation; bootstrap trust documented separately from runtime verification; emergency recovery.
- HARNESS_MAINTENANCE and BENCHMARK keep every security-critical protection active and cannot cross a decision gate.
- Profiles STANDARD, STRICT (enterprise default), HIGH_ASSURANCE.

## J. Final distribution, upgrade and migration model

**Release.** Source repository EGO, release branch, tag `vX.Y.Z` equal to `package.json` version, tag commit reachable from the release branch; protected environment holds the Ed25519 signing key(s) and the registry token; publication only there. Pipeline: typecheck → lint → unit → integration → conformance → adversarial (network-free suite included) → secret and redaction corpora → context-budget tests → authority-diff and version discipline (compiled authority table and trusted-key list diffed against the previous release tag; PATCH rejected on any diff; MAJOR/MINOR classified per Q84) → build with `SOURCE_DATE_EPOCH` → package → `npm sbom` → external manifest → sign with each active key → release assets → `npm publish ./ego-X.Y.Z.tgz` → `npm pack @tarscoff/ego@X.Y.Z` and fail unless the hash equals `SHA256SUMS`. Artifacts per Q82. Identity per Q77: `runtime_sha256` is what pins, caches and `version` use; `tarball_sha256` verifies transport.

**Trust.** Machine-local trust store `~/.ego/trust/keys.json` (under `EGO_HOME`), seeded from the installed global package's `release-keys.md` at first run under bootstrap trust; extended only when a release verified under a currently trusted, non-revoked key carries `trusted_key_changes` adding a key (the cross-sign); a key removed by such a release's `trusted_key_changes` is flagged revoked for verification; revocations from the launcher's own `release-keys.md` are merged at every launcher start under bootstrap trust; keys are never deleted, revocation is only by flag. Verification of any artifact = at least one `SHA256SUMS.<keyid>.sig` verifies under a trusted, non-revoked key. Rotation: the transition release is signed by both keys and adds the new key; later releases may sign with the new key only; supported older releases are re-signed and republished as additional signature assets so old pins remain syncable. Revocation and compromise: out-of-band revocation notice on the independent channel (M16, mandatory), protected environment and registry token rotated, new key generated there, its fingerprint published on the independent channel, a new-key-signed launcher release published, users reinstall through the bootstrap path and run `bootstrap doctor --reverify`, which re-checks every release record under `releases/` against the trust store and marks in `index/` any identity whose signature-backed records were all verified by a revoked key as REVOKED, so the launcher refuses to delegate to it with an explicit blocker naming the pin and the upgrade target, which `upgrade` then performs entirely on the launcher (Q85). First install: the fingerprint MUST be taken from the independent channel; README and in-package docs are convenience copies; the convenience `npm install -g` path derives its trust from the authenticated registry, TLS and account, plus EGO integrity checks on first execution (tamper detection, not publisher proof), and `version` says so. A trusted launcher verifies a downloaded tarball with `ego distribution verify` before a global upgrade so the chain stays unbroken for high assurance. **Trust promotion.** Trust is a machine-local property of a runtime identity, recorded in the index, never in the pin. `ego sync` obtains, on the launcher and before delegating, the signed release metadata for the pinned identity from any release-metadata source in `ego.sources` (GitHub Release, HTTPS, file), verifies at least one signature against the trust store, checks that the manifest's `runtime_sha256` equals the pinned identity and the cached bytes, appends the metadata under `releases/<hash>/` and raises the index trust to `signed-release (key <id>)`; `ego.version` and `ego.integrity` are untouched. Because GitHub Packages and the signed release carry the same runtime identity, a convenience install is promotable without re-downloading the runtime. STANDARD may operate at `registry (unsigned)` with explicit disclosure in `doctor`, `status` and receipts. STRICT and HIGH_ASSURANCE permit only the pre-promotion set (Q96) until promotion and refuse governed mutation before it; `doctor` prints runtime identity, acquisition, the trust transition and the profile requirement as SATISFIED or NOT SATISFIED. Promotion establishes that the cached bytes match a signed release; it does not retroactively prove the launcher that performed the check, which is why high-assurance first installs verify before `npm install -g` (K18).

**Installation and resolution.** Global package = launcher + runtime; the launcher set runs without any pinned runtime; hard Node ≥ 24 check. Machine layout under `EGO_HOME` (default `~/.ego`): `runtimes/<runtime_sha256>/` immutable runtime bytes, written once by temp-dir-and-rename, never modified, reverifiable by recomputing the hash; `releases/<runtime_sha256>/` append-only release metadata (manifest, `SHA256SUMS`, per-key signatures) added whenever obtained, never overwritten (a copy with different bytes is rejected as a named mismatch; after a rotation the only expected additions are new signature files, and the manifest's `key_ids` and `signed_at` describe the original signing); `trust/keys.json` the trust store; `index/<name>@<version>.json` = { current identity, acquisition records {source, trust level, verified_by_key_id, cached_at}, displaced [{identity, state}] }, one current identity per version string, with precedence, conflict and state rules per Q79; `mirror/` skills, adapters and docs (mutable); `pins/<repo-identity>/` bounded pin history and the provisional pin used during `upgrade` (mutable). Materialization on every launcher invocation (the launcher's own runtime, idempotent), every `sync`, pin-creating `init`, `upgrade` and `rollback`. Pin per Q94; project definition and launcher dispatch per section C; runtime-root stamp and cross-repository rules per section E.

**Sources and verification levels.** npm: `npm pack` acquisition with the user's `.npmrc`; verification = runtime hash equals the pin, plus release signature when a release-metadata source (HTTPS, file or GitHub Release entry) is configured; result `registry (unsigned)` or `signed-release`. HTTPS, file, GitHub Release: `SHA256SUMS` + signature + runtime hash. STRICT+ require that at least one signature-capable release-metadata source be present in `ego.sources`; source order governs acquisition only, and promotion may use any release-metadata source. Tokens come from `.npmrc`, environment or the approved credential source and are never persisted by EGO.

**Sync, upgrade, rollback.** `sync`: ensure a hash-verified cache entry for the pinned identity (materialize the equal global or obtain from `ego.sources`), attempt trust promotion on the launcher from any release-metadata source, migrate the runtime root and rewrite the stamp when the pinned runtime's runtime-state schema is newer and every AVAILABLE member's pin can read it (else BLOCK naming `ego upgrade --workspace`), delegate, regenerate stale generated artifacts; never changes the pin; under declared offline resolves from cache and `file:` sources only and names skipped remote sources. `upgrade --to Y`: acquisition, verification and materialization of Y execute in the launcher's source-adapter module through the exec contract, X only requesting them (offline: cache and `file:` only, else BLOCK naming the missing artifact and suggesting `distribution import`); when X is REVOKED, SUPERSEDED, TAMPERED, missing, a development identity under STRICT+, or below the profile's required trust, the whole operation runs on the launcher and delegates directly to a verified Y with the old-side compilation marked UNAVAILABLE(refused runtime); otherwise X writes the pre-report with breaking, `authority_changes` (EGO-level and effective, compiled against the consumer's layers) and `trusted_key_changes`, delegates to Y with `--migrate-from X` under a provisional machine-local pin; Y runs the migration scripts it ships (generated artifacts regenerated, overlay schema migrated through reviewable scripts with dry-run diff, authored overlays never overwritten), conformance and doctor, then writes `.harness/harness.md` and the runtime-root stamp; failure restores pre-images and leaves the committed pin untouched; the report notes Codex hook re-trust when applicable. `rollback [--to X]`: the same protocol with roles reversed, preceded by a content-executed dry run by the cached target; BLOCK with the exact migration on any unreadable file or record; inverse `authority_changes` and trust-set delta shown; `--acknowledge-authority-changes` required in STRICT+ when authority is relaxed; same tail. `--workspace` variants move all AVAILABLE members together: they execute on the launch repository's pinned runtime; for each member the executing runtime acquires and verifies the target, compiles that member's pre-report from its own layers, and delegates to the target with `--migrate-from <that member's pin>`. A single-member `upgrade` or `rollback` in a workspace with other AVAILABLE members whose pins cannot read the target's runtime-state schema is BLOCKED naming `--workspace`. The stamp BLOCK and the divergence block never apply to `sync`, `doctor`, `upgrade --workspace` or `rollback --workspace`. Registry unavailable: pinned cached → normal; pinned missing → the launcher blocks without fetching and names `ego sync`; `sync` names each source tried.

**Air-gap.** `ego distribution bundle --offline [--skills <set>] [--adapters <set>] [--docs]` (a `sync` network use when run by the administrator) produces `ego-bundle-X.Y.Z.tgz` embedding the unmodified release tarball and its signed release metadata, plus skills, adapters, docs, schemas, licenses, provenance and hashes in its own manifest. `distribution import` verifies the release signature, extracts, recomputes the runtime hash, appends the bundle's manifest, `SHA256SUMS` and signatures under `releases/<hash>/` exactly as `sync` does, records trust `bundle (signed-release key <id>)`, and installs the rest into `mirror/`; unsigned content is cached `bundle (unsigned)` and refused under STRICT+. Bundle hashes are listed in a separate signed file, `BUNDLES.SHA256SUMS` with `BUNDLES.SHA256SUMS.<keyid>.sig`, produced after signing and never embedded in a bundle; `SHA256SUMS` lists only `ego-X.Y.Z.tgz`, `manifest.json` and `sbom.cdx.json`. `distribution import` may also re-materialize a TAMPERED identity after moving the tampered directory aside.

**Migration of existing projects.** What moves into EGO core (rewritten, never copied): single rule table with a canonical enforcer and generated adapter configs; deterministic grant recognition; tier from touched paths; fingerprinted validations and verdicts with STALE by default; write-ledger attribution; JSON receipt validated at Stop; anti-loop caps; MCP trust default-deny; generators byte-diffed; DoR/DoD; test-honesty classification; UI reference fidelity; the three-block reporting rhythm as the receipt's end block; offline and runtime-config rules.

## K. Known limitations, threat model, bootstrap trust, operational limits

1. A process running as the same unrestricted OS user can attempt out-of-band forgery of any local file. EGO guarantees prevent in-band, detect out-of-band, managed protection in HIGH_ASSURANCE; not local cryptographic authorship.
2. Shell writes into a foreign scope or frozen path are detected after execution except the pre-denied classes and the STRICT allowlist rule.
3. Writes outside hooked hosts surface as ambiguous or untracked and are never attributed.
4. `codex-cli` liveness is TTL-only; duplicate Codex processes on one session are undetectable; four Codex capabilities are unverified until conformance.
5. The window between a PreToolUse allow and the actual write is unbounded under a permission prompt.
6. Local git hooks are bypassable with one flag; the model-independent backstop is `harness verify --range` on a protected branch.
7. Stakeholder authenticity cannot be proven; manifest binding proves unaltered questions; the operator's import is the anchor.
8. Prose weakening without any structural or token signal is surfaced, not gated.
9. Cross-machine coordination is out of scope.
10. Windows and network filesystems unverified; Linux `ps` behaviour to verify in CI.
11. GitLab tested against a mock server; Azure DevOps and Bitbucket on fixtures.
12. STANDARD may complete on a stale forge snapshot with disclosure.
13. Wall-clock heartbeats misclassify sleeping laptops, on the blocking side for `claude-code`.
14. Caller authentication for the prompt hook is deterministic but heuristic; `--bare` or disabled hooks run no agent hooks, which STRICT+ detect.
15. Codex trusts hooks by hash; an upgraded or rolled-back EGO hook is skipped until re-trusted; `upgrade`, `rollback` and `doctor` say so.
16. Echo-and-confirm can become reflexive; the cap and exclusions bound the damage.
17. Bounded decision-side excerpts of stakeholder text enter git and model context.
18. **Bootstrap trust.** A freshly installed launcher cannot prove its own authenticity with a key embedded in itself. First-install trust comes from verifying the signed release against the fingerprint on the independent channel (mandatory for high assurance), or, on the convenience path, from the authenticated registry, TLS and account; EGO's own checks on first execution add tamper detection, not publisher proof. A runtime materialized from a convenience install carries trust `registry (unsigned)` until `sync` or pin-creating `init` promotes it from a release-metadata source; STRICT and HIGH_ASSURANCE refuse governed mutation and permit only the pre-promotion set (Q96) until then. Thereafter the launcher verifies every runtime obtained through `sync`, `upgrade` or `distribution import` before it enters the immutable cache; the launcher's own authenticity remains whatever the install path established.
19. **Key compromise.** Recovery is out-of-band by construction; self-verification by a compromised launcher proves nothing; identities verified only by a revoked key become REVOKED in the index and are refused until re-signed metadata is appended.
20. **npm does not verify a local tarball's checksum** without a lockfile and treats `engines` as advisory; EGO verifies hashes and the Node floor itself.
21. **Network scope.** The zero-network guarantee covers activity initiated by EGO-authored code, direct or by spawning a network-capable tool; the hosting runtime and the model communicate with their providers outside EGO's control unless the host exposes that control; tool-initiated traffic is governed at PreToolUse. `doctor` lists the four classified capabilities and their state.
22. **Registry unavailable** with the pin missing from the cache is an explicit missing-runtime blocker; there is no hidden fallback.
23. **Rollback and version consistency.** A runtime that cannot read current authored schemas, policies or the runtime-root stamp is blocked, not faked. Divergent pins across AVAILABLE members of one workspace are tolerated with a warning for read-only work only when every member can read the stamp; any write, claim, adopt, resume or handoff that would cross runtime identities is blocked in every profile; STRICT blocks at task open or adopt; HIGH_ASSURANCE blocks any governed mutation in a divergent workspace; the remedy commands are exempt.
24. GitHub Packages requires authentication even for public packages; provenance attestations on GitHub Packages are undocumented, so EGO's integrity story does not depend on them.
25. **Launcher removed or not on PATH.** Hook shims fail closed (exit 2) and git hooks fail non-zero with a one-line message; `doctor` and SessionStart report PATH resolution; STRICT+ treat it as an enforcement gap, STANDARD warns.
26. **Delegation contract.** Delegation is an in-process dynamic import with a versioned exec contract in the compatibility matrix; contract breaks are MAJOR; the 60 ms hook budget is tested on both paths.
27. **Cache immutability and identity.** Runtime bytes never change under an existing content hash; trust, signatures and provenance live in separate mutable or append-only stores; an official version maps to exactly one runtime identity, and development builds always carry a `-dev.<git-sha>` identity. A launcher compromised before promotion can misreport a promotion (K18); the high-assurance path avoids this by verifying before installation.
